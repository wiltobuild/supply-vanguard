# Supply Vanguard implementation plan

## Selected UI/UX reference

The [homepage reference and shared design direction](../design/README.md) govern future UI work. Use the supplied department-workspace composition, coral accents, pastel equipment cards and large typography for the homepage, adapting its content to the working NICU scope. Carry shared tokens, navigation and components into equipment, ward, coordination and approval screens. SV-003 must implement this direction alongside accessibility and fallback requirements; saving this reference does not mark the redesign complete.

## Product and first release

Help staff find available equipment, understand whether its location is trustworthy, update movements and readiness, and replenish supplies. The 3D ward is a navigable representation of locations, not the source of inventory truth. Start with one Baltimore Children's Center NICU-inspired ward section: six infant rooms, supply room, equipment store, staff workroom and family area. Expand to additional wards only after location mapping and workflows are validated.

Primary users: bedside staff search and report moves; equipment staff clean, maintain and release equipment; supply staff replenish bins; managers monitor availability and audit changes; administrators manage users, facilities and integrations. Do not require patient identity for these workflows.

Existing orbit/walk navigation, supply demo, procedural geometry, GLB exports and reference documentation are imported intact. Twelve GLBs and vendored Three.js let another agent inspect and run the project without opening the original hosted Site.

Search/highlight expansion, cross-ward borrowing and historical playback below are proposed work, not delivered capabilities.

## Architecture

Reuse the existing generated NICU ward and equipment asset kit in `packages/scene/viewer`: preserve the procedural `ward.js` and `models.js` source, the full ward and cutaway GLBs, and all ten individual equipment GLBs in `assets/` (12 GLBs total). Continue building on this scene and its configuration rather than regenerating or replacing it with an unrelated scene. Preserve stable room/location/equipment IDs and identity mappings, meters/Y-up coordinates, source labels and illustrative, non-surveyed provenance. Validate and refine the existing assets against approved reference evidence; any future geometry corrections must retain traceable source/confidence records and reviewed mapping changes.

Keep the web client, scene package and domain rules separate. The server API owns authoritative inventory state as clients adopt it; local demo storage is not shared production truth. The scene receives stable equipment IDs, location IDs, status, freshness and provenance; meshes are disposable render objects. Keep the list/search workflow fully usable without WebGL. Preserve versioned API contracts while replacing the demo adapter.

Proposed production stack: current browser UI and Three.js initially, Node service and PostgreSQL, managed OpenID Connect authentication, migrations and CI. Provider selection, organizational access requirements and hosting region are decisions for the deployment milestone; no paid services are provisioned by this scaffold. Evaluate framework migration only if it simplifies required workflows; do not rewrite the scene to change UI frameworks.

Data entities: organization, facility, ward, location (hierarchical, stable external key), equipment type, serialized equipment, equipment observation, movement/status event, supply SKU, bin stock, stock transaction, replenishment task, maintenance job, user membership and integration source. Equipment is serialized; consumable quantities belong in stock transactions rather than duplicated equipment records. Store quantities in declared units. All server records carry tenant IDs and version/audit metadata.

Equipment commands validate allowed transitions, permissions and expected version in one database transaction, persist the new state and immutable audit event, and return conflict details on stale edits. Event records include actor/source, observed time, received time, correlation and idempotency keys. Realtime updates are notifications to refetch or ordered events, never a second authority. Preserve last verified location separately from last administrative edit: changing maintenance status must not falsely refresh physical location confidence (the demo currently uses one timestamp).

## Delivery sequence and acceptance gates

### 0 — Bootstrap (delivered)

Repo, local runnable demo, imported reusable 3D assets, full plan, seed backlog, concurrent claiming CLI, contributor instructions and checks. Gate: demo serves, models validate, domain and claim race tests pass, shared board is visible on GitHub.

### 1 — Contracts and trustworthy scene (SV-001–003, parallel)

Define versioned equipment/location/event schemas and source/freshness semantics. Extract ward configuration from procedural code, document meters/Y-up axes, map locations to coordinates, and validate bounds and asset references. Make equipment list workflows accessible, provide loading/error and WebGL fallback states, support narrow screens and keyboard use. Gate: unknown locations fail safely, every asset has a stable identity, and moving an asset updates both list and scene without changing identity. Preserve labels distinguishing verified sources from estimated geometry.

### 2 — Shared system of record (SV-004–008)

Build local development database, migrations, constraints, seed data and transaction tests. Integrate login and membership-scoped permissions. Add equipment query/update endpoints and immutable events with optimistic concurrency. Replace browser persistence with an adapter using API state; implement reconnect/refetch and conflict recovery. Add QR or barcode labels and manual check-in with source attribution. Gate: two clients see consistent changes, stale writes cannot overwrite newer state, unauthorized cross-tenant reads/writes fail, and duplicate check-ins are idempotent.

### 3 — Supply and equipment operations (SV-009–012)

Supply SKU/bin counts, adjustments and restocking as ledger transactions; low-par alerts and replenishment work queues; equipment cleaning/maintenance state transitions and availability filters; audit search/export. Gate: concurrent replenishment cannot double-add stock, maintenance assets cannot be presented as ready, every correction retains audit history, and exports obey permissions.

### 4 — Sensor integrations and confidence (SV-013–014)

Implement provider-neutral observation ingestion with device authentication, replay protection, idempotency, observed/received timestamps and dead-letter handling. Start with a simulator. Add one real RFID/BLE/RTLS provider only after hardware and access are chosen. Resolve late/out-of-order/conflicting observations using explicit rules and surface uncertain or stale locations. Do not infer precise coordinates from a room-level signal. Gate: replayed and delayed data cannot teleport equipment backward; offline devices show stale state, and manual overrides are audited and time bounded.

The [historical equipment location playback proposal](#future-work---historical-equipment-location-playback) builds on the shared record and confidence contracts above. Settle its historical query, baseline and replay policies before scheduling implementation; it does not require a real sensor integration or change existing task ownership.

### 5 - Validation and production pilot (SV-015-018)

Obtain approved measured drawings or authorized measurements before claiming architectural accuracy. Review geometry and equipment placement with staff, maintaining a per-element source/confidence register. Add end-to-end tests, performance budgets, supported browser checks, backup/restore exercises, observability, deployment/rollback and operational runbooks. Run a limited ward pilot with synthetic data first, then approved operational data. Gate: staff can find/check in/replenish equipment, measured latency and errors meet agreed targets, restore and rollback are demonstrated, and known limitations are signed off.

## Future work - equipment discovery, requests and cross-ward borrowing

### Search and matching equipment in the ward

Make equipment searchable by type and serialized instance (stable ID/label), with location, readiness/availability and freshness filters. Selecting a type icon or list option, or choosing Show all of this type from an individual object, must reveal/highlight every matching authorized item in the active 3D ward. Keep the selected instance distinct from the matching group, preserve identity and selection as filters change where still authorized, and provide clear filter/clear actions. Report matching counts and distinguish located, unknown and stale items; do not hide unknown items from totals or label stale/unknown positions as currently verified. Show per-item location, last observed/source, freshness and availability independently; a known room does not imply an item is ready to borrow. Provide an equivalent searchable, keyboard-accessible list and clear focus/selection feedback without WebGL. In historical mode these filters use the selected-time projection and remain read-only.

### Requests, holds and partial fulfillment

Preserve the authenticated core workflow criteria in SV-020-022 without restructuring the live board. Requests may contain multiple items/quantities; concurrent assignment of a serialized item must have exactly one winner, with atomic conflict handling and retry/idempotency semantics. SV-020 requests/assignments are in review in PR #11; independent stacked holds (SV-021) and partial fulfillment/safe returns (SV-022) remain planned work. This plan uses the stated criteria, not an unverified external artifact.

Represent dirty, fault, maintenance and unknown holds independently, allowing several to apply at once. Clearing one must not clear the others or make equipment available while another blocking hold remains. Require the matching authorized role to clear each hold and retain decision provenance; settle the exact role mapping before implementation. Availability must account for holds, reservations/assignments, pending loans and physical custody rather than a single optimistic status flag.

Track requested, assigned/reserved, dispatched, received, returned, cancelled and missing quantities/instances distinctly. Support partial fulfillment and cancellation of only the outstanding eligible remainder. Cancellation must never make already dispatched equipment available or imply its return. A dirty return remains held until authorized clearance; a missing item remains unavailable pending an audited resolution. Reconcile these states with existing request work before adding borrowing so two workflows cannot allocate the same item.

### Authorized cross-ward inventory and borrowing

Let staff see equipment inventory and readiness across permitted wards within authorized tenant/facility boundaries to locate potential loans. Show each ward's available, held, reserved/on-loan and uncertain inventory with freshness and location evidence, without exposing unauthorized ward totals or item details. Define separate server-enforced permissions to view inventory, request a loan, approve it, dispatch/transfer it, receive it and resolve returns or exceptions; viewing another ward never grants approval authority.

Separate the permission decision and reservation/loan state from physical custody. Automatic or human permission does not move an item in the scene. Only an authorized recorded dispatch/transfer/receipt or location observation can change the applicable custody/location state under the agreed event contract. A reservation can reduce borrowable availability while the item remains physically in its source ward. Describe in-transit, received, overdue/expired and unresolved custody truthfully rather than relocating equipment from a request alone.

Allow each source ward to configure an approved surplus policy by eligible equipment type. Automatic borrowing permission is permitted only when verified ready available stock, after safety reserves, existing reservations/pending loans and the requested quantity, satisfies that policy. Account for overlapping reservations/loans by identity without double counting. Low-stock requests require an authorized source-ward approval; unknown, stale, unverified inventory or unconfigured thresholds must never autoapprove. Human approval does not bypass physical readiness or erase holds. Decide safety reserve quantities, surplus thresholds, eligible types, verification/freshness rules, approval roles and whether partial approvals are allowed before implementation; no values are chosen here.

Make the policy decision and reservation atomic and concurrency-safe across both requests and loans. Lock/version the relevant inventory and allocations so simultaneous requests cannot both consume the same surplus, and prevent duplicate/replayed loans with idempotency and durable decision records. Revalidate policy, authorization, readiness and allocations at agreed lifecycle transitions, including approval/reservation and dispatch; define how changed stock, expired verification, newly applied holds and policy changes affect pending decisions before implementation. Audit the policy version, inventory basis, automated/human decision and actor/source without patient-linked data or credentials.

Define override/escalation, cancellation, expiry, release, safe return and missing-item handling with the operational owner. Expiring permission can release an unused reservation under policy, but must not release dispatched equipment as available. Dirty/fault/maintenance/unknown holds survive transfer and return until matching-role clearance. Cross-ward server queries and all loan mutations must enforce tenant, facility, ward and role isolation, including guessed IDs, concurrent requests and replayed commands.

### Additional Hopkins-inspired wards and sequencing

Extend the shared configurable scene/asset system to additional Hopkins-inspired wards using stable ward/location IDs and explicit equipment mappings. Preserve the existing generated NICU, procedural source, twelve original GLBs and additive equipment models, including the separately requested fifteen; reuse them rather than replace them with unrelated scenes. Keep each ward's provenance and confidence visible. Do not claim authenticated Hopkins architectural accuracy, measured dimensions, real-time tracking or architectural sign-off without approved source material, reuse rights and ward/facilities validation. Missing drawings are a documented accuracy limitation, not permission to invent measured geometry.

Sequence discovery against stable identity/type and query contracts, then reconcile shared request allocation, stacked holds and partial-return semantics (SV-020-022) before implementing cross-ward loan policy. Historical playback below depends on recorded location/custody evidence and cannot infer movement from permission. Additional wards require authorized inventory scoping, mapping and source review; accurate recreations depend on SV-015 validation. These are future dependencies and review gates, not dates or new board claims. Settle thresholds, role mappings and lifecycle policies with owners before implementation, and add tasks only through later coordinated planning.

### Acceptance scenarios

1. Searching IV pumps or selecting a pump/type icon highlights all matching items in the active ward, retains distinct serialized IDs and selection, and reports correct located/stale/unknown counts. Clearing or changing the filter updates scene and list consistently; the same search and selection work without WebGL and with keyboard/screen reader controls.
2. An authorized user sees permitted wards' inventory/readiness and can request several items; a viewer without request/approval authority cannot mutate loans. Unauthorized tenant/facility/ward IDs and totals remain inaccessible server-side.
3. Under a synthetic test policy with five verified ready units, two safety-reserve units and one existing reservation, a request for two may qualify for automatic permission; a request for three requires source-ward approval. These fixture values are not business defaults. Unknown/stale/unverified stock or missing policy never autoapproves.
4. Two concurrent requests competing for the same remaining surplus cannot both win; automated permission and reservation commit together or neither commits. Replayed requests do not create another loan. A newly applied hold or reduced stock is caught at revalidation before dispatch. Permission/reservation alone leaves physical scene location unchanged.
5. Competing multi-item assignments produce exactly one winner per serialized item. Stacked dirty and fault holds survive clearing only one; an unauthorized or nonmatching role cannot clear the other. The item remains unavailable until every required clearance and custody condition is satisfied.
6. Request three, deliver two, cancel the remainder, return one dirty and report one missing: preserve the fulfilled/cancelled quantities, dirty hold and missing exception separately. Cancellation does not release either dispatched item; neither the dirty return nor missing item becomes borrowable. Audit and safe retry behavior cover each transition.
7. Switching between configured wards preserves stable identity/mapping and honest source labels. A loan's permission does not relocate its model; recorded custody/location transitions do. Historical replay uses those recorded transitions with unknown/gap states where evidence is absent.

## Future work - historical equipment location playback

This proposed timeline lets staff select a day and rewind to see the recorded locations of multiple serialized items together. Playback is not implemented and has no delivery date. It depends on the shared system of record, stable identity mappings, authorized historical queries and agreed observation/confidence rules; manual observations can support it without continuous sensor coverage. This plan addition creates no implementation claim or live-board migration.

### Experience and scene reuse

Provide a day/time selector, scrubbing and rewind/forward seek, play/pause, a bounded set of playback speeds, and a prominent Return to live action. Always display the selected timestamp, ward IANA time zone and UTC offset, plus a visibly distinct, read-only Historical mode label. Keep every displayed item's state synchronized to the same selected instant. Preserve stable equipment identity and selection across seeks, refreshes and mode changes; if the selected item has no authorized historical location, retain its identity with an explicit unavailable/unknown state.

Reuse the existing generated NICU scene, procedural ward and all twelve GLBs with their stable equipment/location IDs and illustrative, non-surveyed provenance. Additional assets, including the separately requested fifteen models, may extend this kit without replacing existing assets. Room-level observations justify only representative placement within the recorded room, clearly labeled as illustrative: never invent precise coordinates, continuous tracking or interpolated movement paths between observations. Unknown or unavailable locations must not be positioned as if known. Provide the same timeline controls, selected-time states and accessible per-item history in a keyboard- and screen-reader-usable list without WebGL; follow the shared design direction and reduced-motion preferences.

### Historical reconstruction and time semantics

Build a selected-time projection from authorized recorded observations and applicable location events, starting from a documented initial known state valid at or before that instant, or an explicit unknown state. Today's mutable equipment location or last-verified state is not a historical baseline. Define a future initial-state/snapshot contract, including its effective time, provenance and completeness, before implementation. A bounded day query must obtain an authorized pre-window baseline where available; absent an earlier observation or valid snapshot, show unknown rather than borrowing a later location. Retention cutoffs and missing intervals must be shown as history gaps, not evidence that an item remained stationary.

Show last observed time/source and uncertainty, stale, unknown or history-gap labels at the selected time. Evaluate freshness as selected historical instant minus the applicable physical observation time, using a documented threshold policy; a status edit or receipt time must not reset freshness. Settle threshold values and whether historically versioned thresholds are used before implementation, and disclose the applied policy. Last observed is evidence of a location, not a guarantee of where the item physically was between observations.

Build on append-only observations with `observed_at`, `received_at` and stable UUIDs, and events with `recorded_at` and `before_state`/`after_state`. These existing fields do not provide a delivered correction-chain, as-of query or initial historical snapshot contract. Define a normalized replay contract that distinguishes when a physical observation applies from when the system received/recorded it; specify how each eligible event supplies effective location time rather than assuming `recorded_at` is physical observation time. Preserve actor/source, correlation/idempotency and original records. Corrections must append provenance and an explicit supersession relationship, with effective and recorded times, rather than overwrite history; exact correction eligibility and conflict rules remain decisions before implementation.

For reproducible replay, order eligible observations by observed time, then receipt time, then stable record ID as a final deterministic tie-breaker, within a fixed authorized record revision. A UUID tie-break is reproducibility, not chronological or source authority. Settle and version the policy for conflicting sources, equal-time contradictory locations, manual overrides and correction precedence before implementation; surface unresolved conflict as uncertainty instead of treating arbitrary ordering as proof. Define equivalent effective/recorded-time ordering for normalized events and deduplicate events/observations representing the same update. Preserve the existing rules preventing late data from regressing live current state; historical reconstruction is a separate projection.

Use UTC instants for comparison and ward-local dates for selection. Convert each selected ward day to its actual UTC bounds, allowing 23- or 25-hour daylight-saving days. Disambiguate repeated local times with offsets and reject or explain nonexistent local times. Pagination, seeks and ordering must remain consistent across these boundaries.

Label the initial proposed replay as reconstructed history using current authorized records, with an explicit record revision/as-of retrieval time. A late observation or correction may therefore change a refreshed reconstruction of an earlier instant. This is distinct from information actually known at that earlier time, which would additionally require a receipt/recording cutoff and correction visibility as of that cutoff. Decide whether to offer that second mode before implementation; never silently describe reconstructed history as what staff knew then. Both interpretations must remain subject to the viewer's current authorization.

### Live separation, access and availability

Pin the historical projection to a consistent server revision while browsing. Incoming live notifications must neither move the selected timestamp nor silently replace displayed historical states. Indicate when refreshed history is available; an explicit refresh pauses playback, reloads a consistent revision and preserves selected time and equipment identity while explaining that late/corrected records may change results. Define the server snapshot/cursor mechanism before implementation so pagination cannot mix revisions. Return to live must refetch authoritative current state before presenting it as current; show loading/error states on failure. Historical controls must not issue equipment updates or expose operational mutation actions.

Enforce tenant, ward and role access on the server for all historical queries and any later exports, including pre-window baselines, pagination and revision access. Define a minimized historical-location query policy; operators' lack of general audit-log reads must not be solved by widening audit SELECT access. Recheck authorization on subsequent requests and discard inaccessible cached data when access changes. Bound time windows, page sizes, item counts and request cost; do not download an unrestricted audit history to filter in the client. Do not include patient-linked data or retain credentials in historical records, replay payloads or caches. Historical export is outside this implementation scope; any later export requires its own permission-scoped design.

Agree retention, earliest available history, snapshot coverage and deletion/availability behavior with the deployment owner before implementation. Display available date ranges and explicit unavailable/partial-history states; do not promise recovery of unrecorded or expired history. Preserve authorized provenance without exposing restricted actors or locations through history details or gap messages.

### Acceptance scenarios and decisions before implementation

1. With item A observed in room 1 at 09:00 and room 2 at 09:20, and item B in the store at 09:05 and room 3 at 09:40, seeking to 09:30 shows A in room 2 and B in the store. Rewinding to 09:10 and seeking forward again yields identical states across the scene and list, with stable identities and selection.
2. Repeated timestamps and paginated results reproduce the same ordering at a pinned revision. Contradictory sources follow the agreed conflict policy or show uncertainty. An observation for 09:15 received at 10:00, followed by an append-only correction, changes only an explicitly refreshed reconstruction; originals and provenance remain available as authorized. A proposed known-at-the-time view excludes records/corrections not received by its cutoff.
3. An initial state with valid provenance supplies a pre-window baseline. An item with no observation before the selected time is unknown even if its current location is populated. With a synthetic 30-minute stale threshold, a 09:00 observation is fresh at 09:20 and stale at 09:31; later receipt or status edits do not refresh it. Missing or expired history is labeled as such.
4. Room-only moves change representative room placement at recorded effective times without invented coordinates or animated travel paths. Unknown and uncertain states remain distinguishable from verified positions.
5. Live notifications during paused or playing history neither jump the selected time nor silently revise its pinned projection. Explicit refresh retains time/selection and explains revisions. Return to live refetches current authoritative state, including a clear failure path, before enabling live actions.
6. Cross-tenant, unauthorized ward and disallowed-role requests fail server-side, including guessed item IDs, baselines and pagination cursors. Authorized users receive only minimized permitted history; any future export must pass equivalent checks.
7. Without WebGL, keyboard and screen-reader users can select the day/time, seek, play/pause, choose a bounded speed, inspect synchronized item histories and return to live. Verify repeated/nonexistent daylight-saving times, visible zone/offset, reduced motion, loading, empty and partial-history states.

Before implementation, settle source/conflict and correction policies, initial snapshots and event effective-time mapping, replay interpretations, historical role/ward scope, retention, threshold versioning, revision/refresh mechanics, playback speed limits and query limits. Measure initial history load, seek latency, playback responsiveness and memory on representative ward devices, item counts, event densities and network conditions. Agree performance budgets from those measurements separately from the existing pilot targets; these are proposed measurements, not demonstrated playback performance. Implementation tasks and ownership require later coordinated planning.

## Targets to validate during pilot

Initial targets: useful scene within 5 seconds on the agreed ward workstation; responsive orbit at 30 fps or better; API p95 below 500 ms for routine queries; online updates visible within 5 seconds; no lost or duplicated committed inventory transactions. These are proposed acceptance targets, not current performance claims. Measure representative network, asset count and device conditions before committing service levels.

## Safety, access and operations

Use least-privilege memberships (viewer, operator, supply manager, equipment manager, admin), server-side authorization, scoped integration credentials and immutable audit records. Keep secrets outside source control. Define retention/export/deletion and backup policy with the deployment owner. Avoid patient-linked information in the first release. Production readiness and any organizational compliance requirements require their own review; the local demo is not a clinical decision system.

Validate imported JSON and scene boundaries, cap asset counts, and keep dynamic models separate from collision/navigation geometry. Add monitoring for ingestion delay, API errors, stale equipment and failed background jobs. Keep a documented recovery route when WebGL or live updates are unavailable. Add automated accessibility, conflict, authorization and integration replay tests where they verify real user outcomes.
