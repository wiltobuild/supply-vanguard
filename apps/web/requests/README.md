# SV-027: task-local requests, holds and returns

This is a mountable module, not shared-app integration. No host entry point, route dispatcher, server, token flow, role configuration, fixture or package dependency is changed. The only implementation paths are this directory and `apps/web/tests/request-lifecycle.test.mjs`.

## Host contract

Load `styles.css`, then import `createRequestApi` from `client.js` and `mountRequests` from `view.js`. Call `createRequestApi({organizationId, transport})`; transport receives `(organizationScopedPath, {method, body, signal, headers?})` (`headers` only for the clearance-with-evidence command, see below) and must return parsed JSON or throw an error with HTTP `status` and an honest `uncertain` flag for potentially committed writes. It is the existing authenticated host's responsibility to add authentication, JSON encoding, no-store semantics, timeout and access handling. Do not inject a transport that treats non-2xx HTTP as success. This module stores no credentials or browser persistence.

Mount with `mountRequests(element, {api, permissions, role, equipment, equipmentTypes})`. Permissions and role must be the current authenticated membership, never UI-selected authority. Equipment must be current authorized inventory records (`id`, `modelKind`, `version`, `status`); selecting one is not proof it is assignable. Equipment types are authorized strings for the creation form. Empty permissions deny mutation controls. Server authorization is always authoritative.

The host must call `resetAccess()` immediately on identity, organization, role, or view changes; this aborts work and drops protected records, inventory and drafts. Dispose and mount anew with a new API after the host establishes the next authorized context. `dispose()` removes listeners, aborts reads/writes and clears DOM. Repeated mount on the same element automatically disposes its prior module. Closing during a write does not roll back the server; host navigation must disclose that possibility and load server truth upon return.

## Frozen existing contracts

- Create: POST `/organizations/:org/requests` body `{items:[{equipmentType}],note?}`. One entry is one demand unit, 1–20 entries. There is no server creation command key: uncertain creation is not retryable. Reconcile the request list before starting a genuinely new request.
- List: GET `/organizations/:org/requests?limit=100&cursor=...`. All pages are fetched with repeated-cursor detection. The legacy list summaries are never displayed as lifecycle quantities.
- Claim each line: POST `/organizations/:org/requests/:id/items/:line/claim` body `{equipmentId,expectedVersion}`. This expected version belongs to equipment, not lifecycle. Existing exact claim replay semantics are preserved. Multi-item requests are assigned line-by-line, not presented as an atomic bulk operation.
- Read lifecycle: GET `/organizations/:org/requests/:id/lifecycle`, using frozen SV-022 shape with `items`, `summary`, per-line `version`, `assignments`, `holds`, `history`, custody timestamps and `demandCancelled`. UI quantities are derived from these item records, not the legacy summary. Delivered remains cumulative via `receivedAt`.
- Transition: POST `/organizations/:org/requests/:id/items/:line/lifecycle`, body `{action,expectedVersion,commandKey,condition?}`. `action` is dispatch/receive/cancel/return/missing/fail. Return requires an explicitly selected clean/dirty/fault/maintenance/unknown condition. Key/body are frozen for exact retry; every newly requested action receives a new key. A 409 refetches and requires review; 422 exposes readiness blocking. No optimistic assignment release or location move.
- Holds: POST `/organizations/:org/equipment/:id/holds` with `{kind,reason?}`; POST `/organizations/:org/holds/:holdId/clear` with no body; GET `/organizations/:org/holds/clearance-rules` returns `{rules:[{kind,role}]}`. A clear button requires that active hold's matching configured role; no fallback/admin exception. Unknown create/place/clear outcomes require explicit reconciliation rather than assuming replay safety.

## Clearance evidence wiring (SV-027 follow-up, against the PR #32 contract, schemaVersion 1)

Clearing a hold can now carry **evidence**: a reference, an observed time and an optional note. Evidence is a **recorded assertion**; this screen does not check it against any policy, and nothing here says it is sufficient to clear a hold. Whether evidence is mandatory, what counts as enough, and when the legacy clear is retired are open owner decisions. The legacy no-evidence clear stays available, labelled "without evidence (legacy)".

- **What is sent.** `api.clearWithEvidence(holdId, body, idempotencyKey)` posts `/organizations/:org/holds/:holdId/clearances` with body `{schemaVersion:1, evidence:{reference, observedAt, note?}}` and an `Idempotency-Key` header. The body has no actor, tenant, role or authoritative time; the server takes those from the session and its clock. **Host contract addition:** the transport now receives `headers` (for example `{'Idempotency-Key': ...}`) in its options for this one command and must forward them. Every other call is unchanged.
- **Validation before sending.** `prepareClearance` applies the server's rules (reference 1 to 128 safe characters; `observedAt` a real UTC time like `2026-11-10T09:30:00Z` with **at most three fractional digits** and not in the future; note single line, up to 500 characters). Invalid input sends nothing, consumes no key, and shows an inline `role="alert"` error with the field marked `aria-invalid` and focus moved to it. Messages are fixed text that never repeats what was typed. The server stays authoritative.
- **Retries.** The exact prepared body and the key are frozen when the command is created. After an uncertain write (network loss or 5xx), "Retry exact command" resends that same body and key, so the server replays instead of duplicating. A later action gets a fresh key. A new action is refused until an uncertain one is resolved.
- **Responses are told apart.** 400/422 `evidence_invalid` is a validation message. 403 `wrong_role` is a **role refusal**: the screen keeps its records and says the role is not the configured one (it is not a lost session, so it does not wipe anything). Any other 401/403 is still access loss and clears protected data. 422 `no_clearance_rule` says no role is configured. 409 `hold_already_cleared` and 409 `idempotency_conflict` get their own messages and refresh the records. Unknown errors never echo their text.
- **What is shown.** Recorded evidence appears as escaped text with "observed at ... (as asserted by the clearer)", who recorded it and when (server values). A hold cleared the legacy way is labelled "cleared without additional evidence (legacy clearance: only actor and time are recorded)". A cleared hold whose response carries no clearance data is labelled "clearance evidence is not reported by this response": it is never called legacy or evidenced by guess. A placement reason is never evidence.
- **Receipt versus current state.** A clearance response's `hold` (with its evidence) is the receipt; a replay returns exactly the original. `summary` and `holds` are the **current** stack when the server answered and may differ from the first response. The "Last clearance" panel says so, and says when the server did not label the list as current. Clearing one hold never clears another or grants availability.
- **Permission.** The evidence form is shown only for a hold whose kind has a configured rule naming the current role. Without a rule, or for another role, there is no form (the legacy button stays, disabled).
- **Cleanup.** Reset, dispose and access loss erase the last clearance, the issue message, inline errors, drafts and the pending command.

**Tests.** `node --test apps/web/tests/request-lifecycle.test.mjs` runs 34 tests: the 23 frozen ones plus 11 for this wiring (wire format and header, validation and non-echo, first success, replay, role refusal and the other error kinds, invalid precision, exact retry with the same body and key, cleanup and late results, and the rendered form, escaping, legacy and unreported labels, inline errors). `node apps/web/requests/mutation-check.mjs` is a by-hand inventory (not a test) that breaks the module 17 ways and confirms the tests notice each. Everything uses hand-made stand-ins for the DOM, the transport and the clock: no browser, network, server or database.

## Interaction and truthfulness

Pre-dispatch demand cancellation requires an explicit not-in-transit confirmation. Post-dispatch cancellation is labeled demand-only; assignment remains whatever the server returns. Dirty, fault, maintenance and unknown flags are rendered independently. Missing/failed outcomes never imply availability. No overdue deadline, threshold, reconciliation release or business role is invented. All supported lifecycle transitions are available as explicit commands to an authorized writer; server rejects invalid transitions. No action is silently retried.

The view uses semantic labels, forms, buttons, status/alert regions, details and native keyboard controls; restores focused draft controls where possible and focuses status if an action disappears. Drafts survive refresh/conflict, but are erased on navigation/access reset and denied reads. Busy controls prevent repeated submissions. Layout is a one-column reading order at phone widths, with a pastel card grid on larger screens, visible focus, minimum 44px controls, reduced-motion support and dark text on coral.
