# Maintenance panel integration contract

This accessible vanilla-JS panel uses the shared design reference (coral actions, black type, blue/mint/lavender surfaces, rounded forms, visible focus and44px controls). It has no3D dependency or ward/model edits. The shared shell now mounts it at `#/maintenance` and direct `/maintenance` routes with the existing connection. `index.html` remains an offline standalone synthetic preview, not a second public login surface. Actual mounted-browser acceptance remains coordinator-owned and unrun by the author.

The approved shared host exposes only `style.css`, `api.js` and `panel.js` under `/maintenance/`. Its optional injected dispatcher composes existing equipment/maintenance handlers around one existing authorization context; the original same-origin proxy remains supported. Styling is scoped to the maintenance host. Shared-file edits are limited to the exact seven paths admitted by board203 for maintenance integration; unrelated SV008/check-in work and SV019 reservations remain untouched.

An existing authenticated host can instead import `mountMaintenance(root,{api})` from `panel.js` and supply `createMaintenanceApi({organizationId,token})` from `api.js`, or an equivalent already-authorized adapter. `panel.close()` clears drafts/command state/DOM and removes listeners. Session tokens stay in the adapter closure and Authorization header; no URL, storage, issuance endpoint or role picker is added. The standalone page's password field accepts only an existing development session and clears it after connecting. The API remains the permission boundary, so unauthorized history/commands show explicit errors.

Async completions check both panel ownership of the root and their lifecycle generation before updating state or DOM. Close, a replacement identity mounted on the same root, and access-loss invalidation make old reads/writes/history inert; closing an old instance cannot erase its replacement. Current errors remain visible. HTTP status is handled before parsing success JSON, so HTML, empty and malformed 401/403 bodies still trigger authorization cleanup. Inventory 401/403, service 401/403 and session-expired history 401 discard equipment, drafts, pending commands, cursors and history and invalidate older requests. History-only 403 clears audit-protected history/cursor while retaining inventory/drafts covered by the separate inventory permission; it grants no audit access. Genuine uncertain writes (network, unreadable success or 5xx) retain their exact retry body/key until a known result, access loss or close.

Search, selection, service notes and paginated history work with semantic labeled controls. Drafts retain their original expected version through refresh/conflict. After reviewing current state, explicitly choose **Use current version for reviewed draft** to retain text and rebase. Network/5xx/unreadable save outcomes retain the exact pending command and key; **Retry identical command** is the only write action until resolved. Every accepted command/replay refetches authoritative state, because a replay may return an older snapshot. Failed refresh blocks further saves. No automatic write retry, silent overwrite, optimistic availability or freshness update is used.

Service entry completion keeps cleaning/maintenance status and every independent hold. Availability view is labeled **Available, unassigned and unheld**: the API excludes any active merged SV-021 hold before pagination while retaining cleared hold history and unknown physical-location evidence. It does not certify readiness or provide hold-clearance actions. Existing configured matching-role clearance remains in its separate workflow. History is the existing administrative audit stream and explicitly requires audit access. All note/event content uses textContent/value, never dynamic HTML.

Run the commands and read the policy boundaries in [API README](../../../services/api/maintenance/README.md). Browser evidence is an offline module fixture, not shared-app/API reachability. The dedicated tests are not registered in the shared root test loader/CI, which is outside this scope; they must be run explicitly during review.
